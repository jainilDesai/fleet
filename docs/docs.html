Fleet docs

Fleet is a pixel-art office for a team of Claude Code agents on macOS, Linux or Windows (through WSL). You talk to one agent, the CTO. It plans the work, hands tasks to the rest of the team, and you watch all of it happen. Every decision or permission an agent needs from you lands in one Actions list.

Install

You need:

  • macOS or Linux. On Windows, WSL (below).
  • Node 20 or later.
  • Claude Code (claude), signed in.
  • tmux.
  • Optional: the GitHub CLI (gh), signed in. With it, Fleet follows the team's pull requests.

macOS

brew install tmux          # and optionally: brew install gh
npm install -g @jainil_desai/fleet
cd ~/code/my-app           # any git repo
fleet                      # opens this repo's Fleet, http://localhost:7789
fleet home                 # the home page, http://localhost:7788

Linux

sudo apt install tmux      # Fedora: sudo dnf install tmux; Arch: sudo pacman -S tmux
npm install -g @jainil_desai/fleet
cd ~/code/my-app
fleet                      # opens http://localhost:7789 with xdg-open

Install Claude Code with curl -fsSL https://claude.ai/install.sh | bash and run claude once to sign in. For gh, see its Linux install page (apt, dnf, pacman and more).

Windows (via WSL)

Fleet doesn't run on Windows itself, because agents run in tmux. It runs inside WSL, and you use it from your Windows browser. Running fleet in PowerShell or cmd prints these steps.

  1. In PowerShell: wsl --install, restart, and open Ubuntu from the Start menu.
  2. Inside Ubuntu, install Node 20 or later, with nvm (nvm install 22) or NodeSource.
  3. sudo apt update && sudo apt install tmux git
  4. Claude Code: curl -fsSL https://claude.ai/install.sh | bash, then run claude once and sign in.
  5. Optional: gh, from its Linux install page, then gh auth login.
  6. npm install -g @jainil_desai/fleet
  7. Keep your repo in the Linux file system (for example ~/code/my-app), not under /mnt/c: git and agents are much faster there, and file watching works. Then cd ~/code/my-app and run fleet.
  8. Open http://localhost:7789 in your Windows browser (the home page is http://localhost:7788). Fleet tries to open it for you, with wslview or explorer.exe.

Each copy of Fleet works on one git repo: the folder you start it in, or the one you pass with --repo. For several repos, see Several projects.

Right after a release, npm install can fail with ETARGET. Add --prefer-online to fetch the fresh version list.

OptionWhat it does
--repo <path>The git repo the team works on. Default: this folder, or FLEET_REPO.
--port <n>Serve on another port. Default 7789, or FLEET_PORT; if 7789 is taken and you set neither, Fleet takes the next free port. 7788 is the home page's.

To try it without installing:

npx @jainil_desai/fleet --repo ~/code/my-app

From source:

git clone https://github.com/jainilDesai/fleet.git && cd fleet
npm install && npm run build
node bin/fleet.js --repo <path>

Optional on macOS: brew install terminal-notifier makes notification banners clickable. See Notifications.

First run

  1. The Set up your team window opens and checks your machine: tmux, Claude Code and its sign-in, gh, a GitHub remote and your terminal, each with the command that fixes it. Name the project, the lead and each agent, pick their roles, and choose whether PRs get reviewed before merge. Click Create team. This is saved in ~/.fleet, never in your repo. You can change all of it later in Settings.
  2. Click Start team in the top bar. It starts only the CTO. The others start the first time the CTO gives them work.
  3. The CTO may stop on Claude Code's folder-trust prompt (first start only). Click Trust folder in Action items or its drawer.
  4. Click the CTO, open the Messages tab, and type what you want built. Approvals and questions come to Action items.

Open in terminal attaches a terminal window to the agent's tmux session. When Fleet can't open one, it shows the tmux attach command to run yourself. The setup checks show which terminal it will use.

  • macOS: iTerm if you have it, else Terminal.app. The first time, macOS asks whether Fleet (your terminal or Node) may control it. Allow it once.
  • Linux: the first installed of x-terminal-emulator, gnome-terminal, konsole, xfce4-terminal, kitty, alacritty, wezterm and xterm. It needs a desktop session; over SSH, copy the command.
  • WSL: a new Windows Terminal tab in your distro, else a Linux terminal through WSLg.

Several projects

Run fleet in each repo. A second copy takes the next free port and says which. fleet in a repo that already has a copy just opens it.

  • fleet --list shows every running copy, and the home page every project. The ⇄ switcher in the top bar jumps between them, and the Fleet logo goes to the home page.
  • Each repo gets its own team, tmux sessions and worktrees. Two repos with the same folder name never share one.
  • Two checkouts of the same repo can each run a team: new agent branches are named fleet/<project>/<agent>. Until an agent reports its PR, a PR for a shared task number may show as unclaimed in both teams.
  • Only one copy raises notification banners and writes history.

Start at login

Fleet can run in the background from login, one login item per repo.

fleet --autostart          # start at login for this repo, in the background, and start it now
fleet --stop               # stop this repo's copy for now; it starts again at the next login (--all: every repo)
fleet --start              # start the background copy again now
fleet --no-autostart       # turn auto-start off and stop the background copy
  • It's for the repo you set it up from (or --repo <path>). Run it in another repo to start that one at login too.
  • Add --port <n> to --autostart to use another port.
  • The background copy doesn't open a browser tab. The home page links to it.
  • The first fleet --autostart also starts the home page at login (fleet home --no-autostart turns that off).
  • It restarts if it crashes and logs to ~/.fleet/fleet-<project>.log.
  • On macOS it's a standard LaunchAgent at ~/Library/LaunchAgents/com.jainildesai.fleet.<project>.plist. A login item from an older version keeps working, and is replaced when you run fleet --autostart again.
  • On Linux it's a systemd user service at ~/.config/systemd/user/fleet-<project>.service (systemctl --user status fleet-<project>). To start it at boot without logging in, run loginctl enable-linger "$USER" once.
  • On WSL it's the same service, and needs systemd turned on in WSL (see Troubleshooting). It starts when WSL does, not when Windows starts.
  • Install Fleet globally first: --autostart refuses to run from npx, whose cache can be cleared.

If you update Node through nvm, run fleet --autostart again. Fleet reminds you when you start it by hand. If you set up auto-start before 0.3.0, also run fleet --autostart again from your repo, or the background copy can't start.

Stopping

  • One agent: open it and press Stop in its drawer.
  • The whole team: Settings → Team → Stop team… (disabled while no agent runs) lists who is running and asks first. Stop agents ends their Claude Code sessions. Committed work, worktrees, branches, plans and the team stay, and Start team brings them back.
  • Idle agents, automatically: Settings → Workflow → Stop idle agents after (1, 3 or 7 days, or Never; 3 by default). Every 15 minutes Fleet stops a running agent that has been idle that long: no turn, no question or open Action item, no queued message, no unsent text at its prompt. An idle agent does nothing on its own, but its session holds memory, and waking it days later re-sends a long context that's no longer cached, which is expensive. The activity feed says who was stopped, and Start team or a new task starts it again as a fresh session with its role and task. The idle clock is each agent's last state change or activity line, saved in the project's history.json, so it survives a Fleet restart.
  • The team and Fleet: Stop agents and quit Fleet also exits Fleet, and the page says so. Start it again with fleet in the repo, or fleet --start if it starts at login. It exits cleanly, so the login item doesn't restart it before then.
  • From a terminal: fleet --stop stops this repo's Fleet, fleet --stop --all every one, and Ctrl-C a copy you started in a terminal. These leave the agents running in tmux.

Home page

fleet home (or fleet open, or fleet outside a git repo) opens Fleet's home page at http://localhost:7788, the one address to remember. It runs in the background, starts if it isn't running, and also starts whenever you run fleet in a repo. It's light: no repo, no agents, no tmux.

  • Header: how many projects Fleet knows, how many run, and the total cost.
  • A card per project (every repo Fleet has run in): repo path, running or stopped, its URL, agents running, how many things need you (its Action items), open PRs and cost. Open goes to the project, Start starts it in the background (its login item if it has one), Stop is fleet --stop for that repo.
  • A project whose repo folder is gone is dimmed, with Forget: after asking, it deletes only Fleet's folder for it (~/.fleet/projects/<project>), never a repo.
  • Cost is the API-equivalent cost of the project's agents' sessions (subagents included), for today, the last 7 days and all time, from ~/.fleet/history.json. On a Claude plan you don't pay this per session. A session counts on the day it last ran.
  • It updates every few seconds. In every project, the Fleet logo in the top bar links back to it.
fleet home --autostart     # start the home page at login (the first fleet --autostart does this for you)
fleet home --no-autostart  # stop starting it at login, and stop it

Its login item is com.jainildesai.fleet.home on macOS and fleet-home.service on Linux and WSL. fleet --stop --all and fleet --no-autostart --all include it. FLEET_HOME_PORT moves it to another port.

Upgrading from 0.5 or earlier: projects used to start at 7788, so a project's login item may be pinned there. The first time the home page starts, Fleet moves that login item to the next free port from 7789, restarts it, and says what moved. Its agents keep running in tmux. Agents started before the move still call 7788 for their hooks and Team MCP; the home page passes those calls on to their project, so they keep working while it runs. They use the new port from their next start.

Install as an app

The home page installs as an app with its own window, Dock or taskbar icon, and Spotlight entry.

  • Chrome or Edge: open http://localhost:7788 and click the install icon in the address bar (or ⋮ → Cast, save and share → Install page as app).
  • Safari (macOS Sonoma or later): File → Add to Dock.

Then open it like any app, for example Spotlight → "Fleet". Projects open in your browser, since each runs on its own port.

Update and uninstall

npm install -g @jainil_desai/fleet@latest    # update
npm uninstall -g @jainil_desai/fleet         # remove

If you turned on start at login, run fleet --no-autostart before you uninstall. Fleet keeps its own files in ~/.fleet. Delete that folder to remove its teams, plans and history.

The office

Every team member is a character at a desk. The desk shows its state: working, idle, needs you, or in review. The top bar shows how many agents are running and how many things are waiting on you.

The plan wall holds the boards and tasks the CTO creates, with status (to do, in progress, in review, done, blocked) and owner. Tasks update as agents report back and as their pull requests are reviewed and merged.

Click an agent to open its drawer:

  • Task: what it's working on, the task's notes, and its branch.
  • Messages: everything between you, the CTO and that agent, rendered as Markdown (headings, lists, tables, code). Long replies start collapsed with Show all.
  • Open in terminal: attaches to the agent's tmux session (tmux attach -t fleet-<repo>-<agent>). You can read or type into the real Claude Code session.

The team

A new project starts with a CTO (the lead) and five roles. Each role has a short role text, a model and a Claude Code permission mode. You can edit all three in Settings → Team.

RoleDoes
CTOTalks to you, plans the flow, creates and assigns tasks. Never writes app code or deploys.
PlannerTurns a request into a plan that follows the repo's own rules. Doesn't change code.
ImplementerBuilds the approved plan on its branch and commits.
QAChecks out the branch, installs, tests, and reports pass/fail with evidence.
ReviewerReviews the diff for bugs and simplicity, ranked by severity.
DeployerDeploys only when you asked, and asks you to approve each deploy first. Starts in default permission mode.

The default role texts are generic. They follow your repo's own instructions (CLAUDE.md) and use any skills you have. See Customise your team to make them your flow.

Actions

Actions is one list of everything that needs you.

  • Questions and approvals. An agent asks with ask_user, for example "Approve plan: …" or "Approve deploy to production: …". Mark it Done or Dismiss it. A waiting agent continues with your answer.
  • Permission prompts. When Claude Code asks to run a command or edit a file, the request shows here with the full command. Allow or Deny it from the browser, or answer in the terminal. Either one closes the other.
  • Agents waiting in their terminal, for example on the folder-trust prompt, with Open in terminal.

A production deploy is labelled ⚠ PRODUCTION deploy: <branch>, so it never looks routine.

Nothing is allowed automatically. Agents can do whatever their permission mode allows. Anything that needs approval waits for you.

Customise your team

Out of the box every agent is generic. Make it work the way you do in Settings → Team.

Pick a role. The Role menu (in Settings → Team, Add an agent and Set up your team) lists the built-in roles (Planner, Implementer, QA, Reviewer, Deployer, Developer), the roles you saved, and New role… to name your own. Picking a role gives the agent that role's ROLE.md, skills and permission mode. If you changed the agent's ROLE.md or skills, Fleet asks first: Replace or Keep mine.

Then open More, for any agent, the CTO included:

  • Role. Rewrite what the agent does, or click Load role from file… to use a Markdown file. Fleet adds the team, the rules and the tools around it.
  • Skills. Paste a SKILL.md or click Load SKILL.md…, give it a name, and click Add skill. Fleet writes it to .claude/skills/fleet-<name>/SKILL.md in that agent's worktree, where Claude Code loads it. It's never committed, and the repo's own skills are never touched. A skill without frontmatter gets a name and description added. Each agent can have up to 20 skills of up to 100 KB each.
  • Save as my role. Saves the agent's ROLE.md and its skills as your own version of the role, for every project. On any repo, the next agent that gets that role (a new team, an agent you add, or picking the role in the menu) starts with that text and those skills. Agents you already have keep their own copy. Delete my role removes a role you named; Reset to built-in removes your version of a built-in role. Both ask first.

Changes apply the next time the agent starts.

How skills reach agents

  • Skills in ~/.claude/skills (or the repo's .claude/skills) work for every agent.
  • A role's own skills (saved with Save as my role) go to every agent that gets that role.
  • Skills added under Skills for this agent go to that agent only.
  • The built-in role texts tell agents to use a matching skill when they have one, for example for testing, code review or deploys. You can also name a skill in a role: "Test UI changes with the browser-test skill."

Where saved roles live

In ~/.fleet/roles/: <role>.md is the ROLE.md (cto.md for the lead, otherwise the role name in lowercase without spaces, such as qa.md or datascientist.md), and <role>.skills/<skill>/SKILL.md holds its skills. A role you named in Fleet keeps its display name in the file's first line (<!-- fleet-role: Data Scientist -->). You can write these files by hand too: a plain qa.md works as before.

For example, ~/.fleet/roles/qa.md:

You are QA. You test the branch the lead names and report pass/fail with evidence.

- Run `npm ci && npm test`, then test the change in the browser with the `browser-test` skill.
- Only use the staging environment; never production.
- Report what you ran, what passed, what failed (exact output), and what you couldn't test.

Pull requests

With gh signed in and a GitHub origin, Fleet polls the repo's pull requests. It links each one to its task and agent, and reacts:

  • Review comments go to the PR's author.
  • A passed review goes to the CTO.
  • A merge marks the task done.

Only PRs from the team's own branches count. PRs from forks are ignored.

In Settings → Workflow you choose the review tool (CodeRabbit, Greptile, Copilot, a human, or a custom check), whether you or the CTO merges, and after how long idle agents are stopped (see Stopping).

Notifications

Fleet still watches every Claude Code session on your machine. It sends a banner when one needs you or finishes a long turn, even with the page closed.

  • macOS: a notification banner. With terminal-notifier installed, banners are clickable.
  • Linux: notify-send when it's installed (sudo apt install libnotify-bin), without a click action.
  • WSL: no banners. The events still show in Fleet.

0.3.0 removed the old Agents, History, Usage, MCP and Plugins pages. History is still recorded in ~/.fleet/history.json, but isn't shown in the UI.

How it works

  • Agents. Each one is claude running in a tmux session named fleet-<repo>-<agent>, started through your login shell so it has your usual PATH. The CTO starts with Start team. The others start the first time they get a task or a message. They keep running if you close Fleet.
  • Worktrees. Each agent works in its own git worktree at ~/.fleet/projects/<repo>/<agent>, on a branch fleet/<agent> taken from the default branch. Your own checkout is never touched.
  • Team tools. Agents talk to Fleet through a small MCP server at http://127.0.0.1:<port>/mcp: list_workers, get_status, list_tasks, create_board, create_task, update_task, assign_task (lead only), get_my_task, set_my_status, ask_user and send_message.
  • Live state. Claude Code hooks in each worktree post to Fleet when an agent starts a turn, uses a tool, needs input or stops. A message for a busy agent is held and handed over when its turn ends.
  • Permission prompts. They reach Actions through Claude Code's PermissionRequest hook. Fleet holds that request open until you answer.
  • Files in each worktree, all excluded from git through the repo's info/exclude: .fleet-role.md (the role text), .claude/settings.local.json (the hooks), .claude/fleet-mcp.json (the MCP connection) and .claude/skills/fleet-*/ (skills you attached). The files that hold the agents' access token are readable by you only.
  • State lives in ~/.fleet/projects/<repo>/: team config, plan, action items, the inbox and recent message history. A restart picks up where it left off.

Privacy

What
ReadsWhat Claude Code writes under ~/.claude (session registry and transcripts), and the agents' own transcripts to show their replies.
WritesEverything Fleet keeps is in ~/.fleet. In your repo, Fleet adds git worktrees and the excluded files above. It doesn't change your own checkout or your Claude Code settings.
SendsFleet itself only calls GitHub through your gh login, to read the repo's pull requests. No telemetry. Your agents are ordinary Claude Code sessions and use your own login.

Security

Fleet listens on 127.0.0.1 only. Every action from the page (starting agents, sending messages, answering permissions) needs a per-run token embedded in the page Fleet serves. Any request whose Host header isn't localhost is rejected, which blocks DNS-rebinding attacks from other websites. Agents reach the hook and MCP endpoints with a separate agent token.

Agents can do whatever their permission mode allows. Prompts that need approval wait for you, and Fleet never approves one on its own.

Compatibility

The team runs on Claude Code's documented hooks and MCP support. Fleet also reads agents' transcripts to show their replies, and detects prompts in the tmux pane. Neither is a documented stable format. If an update breaks something, please open an issue with your claude --version.

Limits

  • macOS and Linux. Native Windows isn't supported: use WSL.
  • Clickable banners are macOS-only; WSL shows no banners.
  • One repo per copy of Fleet; run one per repo (see Several projects).
  • Each agent's worktree starts without node_modules. QA installs before it tests.

Troubleshooting

"… is not inside a git repository"

You passed --repo (or FLEET_REPO) with a folder that isn't in a git repo. Run fleet from your project folder, or pass the right path. Plain fleet outside a repo opens the home page.

"tmux is not installed"

Run brew install tmux (Linux and WSL: sudo apt install tmux), then start Fleet again.

An agent is stuck and nothing happens

It's probably waiting on Claude Code's folder-trust prompt. Find it in Actions and click Trust folder, or Open in terminal and answer it there.

Open in terminal does nothing

On macOS, macOS blocked Fleet from controlling your terminal. Fleet shows the tmux attach command to run yourself. To fix it, allow it in System Settings → Privacy & Security → Automation, then try again.

On Linux, Fleet found no terminal app, or no desktop session (it was started over SSH or as a background service). Install one (for example sudo apt install xterm) or copy the command. On WSL, install Windows Terminal.

"Fleet doesn't run on Windows itself"

You ran fleet in PowerShell or cmd. Install it inside WSL instead: see Windows (via WSL).

"Start at login needs systemd" (WSL)

Add these lines to /etc/wsl.conf in your distro, run wsl --shutdown in Windows, open the distro again and run fleet --autostart again. Or just run fleet in a terminal.

[boot]
systemd=true

Fleet is slow on WSL

Move the repo from /mnt/c/… into the Linux file system (for example ~/code). Windows drives are much slower from WSL, and file watching doesn't work there.

"This repo has no commits yet"

Agents' worktrees start from a commit. Make a first commit, then run fleet.

"Port 7789 is in use"

You passed --port (or FLEET_PORT) and something else uses it. Leave both out and Fleet picks a free port, or run fleet --list to see the copies already running.

A permission prompt disappeared from Actions

Fleet holds a permission request for up to 10 minutes. If you don't answer in time, or Fleet restarts, the agent asks in its terminal instead. Answer it there with Open in terminal.

The background copy doesn't start after upgrading

Run fleet --autostart again from your repo. Do the same after updating Node through nvm or reinstalling Fleet. Fleet warns you when the login item points at a Node or Fleet that's gone.

"Fleet isn't built yet"

You're running from source. Run npm install && npm run build in the Fleet folder first.

Development

npm install
npm run build              # hq/ → public/ (the office UI) and dist/hq.mjs (the team server)
npm test                   # node --test
node bin/fleet.js --repo <path> --port 7799 --no-open
npm run dev                # Vite dev server for the UI, proxied to Fleet on 7789

The office UI (React, pixi.js) and the team server (TypeScript, MCP SDK) live in hq/. npm run build bundles both, so the published package has no runtime dependencies. public/ and dist/ are build output and aren't committed. This site lives in docs/. Issues and pull requests are welcome on GitHub.
